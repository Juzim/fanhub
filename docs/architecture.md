# Архитектура FAN-HUB

## Поток данных персонализации

```
Регистрация → выбор клуба (favorite_club)
      │
      ▼
Взаимодействия пользователя ──► Interaction (user, club, type, weight)
  (чтение новости, просмотр           │
   видео, лайк, интерес к матчу)      │
                                       ▼
                        recommender.build_affinity_dataframe()
                        агрегирует Interaction в матрицу
                        user_id × club_id → affinity_score
                                       │
                                       ▼
                        KNNBasic (Surprise, collaborative filtering,
                        user-based, cosine similarity) находит
                        пользователей с похожим профилем интересов
                                       │
                                       ▼
                        get_top_clubs_for_user() — ранжированный
                        список клубов (явный любимый клуб всегда
                        приоритетнее предсказаний модели)
                                       │
                                       ▼
                        services.get_recommendations() подбирает
                        свежие Article/Video/Match/Product по этим
                        клубам → кэшируется в Redis на 15 минут
                                       │
                                       ▼
                        core.views.dashboard() рендерит
                        "Рекомендации для вас" на главной странице
```

## Почему именно так

- **Явный сигнал важнее неявного.** Выбор любимого клуба в профиле — самый
  сильный и надёжный сигнал об интересах, поэтому он всегда добавляет
  наибольший вес в `get_top_clubs_for_user()`, а не полагается только на
  предсказание модели.
- **Fallback при малом объёме данных.** Пока в системе меньше 5
  взаимодействий, `train_model()` возвращает `None`, и рекомендации строятся
  на собственной истории пользователя (без CF) — это защищает от пустой
  или случайной выдачи на старте, когда обучающих данных ещё нет.
- **Кэш в Redis, а не пересчёт на каждый запрос.** Обучение модели —
  недешёвая операция; в проде она обычно выполняется по расписанию
  (cron / Celery beat), а не синхронно при каждом открытии дашборда.
  Здесь кэш инвалидируется точечно: при новом взаимодействии или смене клуба.
- **Interaction — единый лог для всех типов действий.** Это упрощает и
  переиспользование для страницы Analytics (просто агрегаты по тому же
  логу), и добавление новых типов сигналов в будущем (например, участие
  в фан-чате) без изменения модели CF.

## Демо-сценарий для защиты (соответствует ТЗ, шаги 1–9)

1. Регистрация нового пользователя, выбор ФК Актобе.
2. Dashboard сразу показывает контент, отфильтрованный по Актобе
   (новости/видео/матчи через `Article.objects.filter(club=...)` и т.д.).
3. Пользователь читает 2–3 новости и смотрит видео Актобе — каждое действие
   создаёт `Interaction` с соответствующим весом.
4. На странице Analytics видно, как «Актобе» становится доминирующим в
   `interest_breakdown`.
5. Пользователь меняет любимый клуб в профиле: Актобе → Кайрат
   (`User.change_favorite_club`).
6. Кэш рекомендаций инвалидируется, dashboard при следующей загрузке
   показывает контент Кайрата — визуально наглядная демонстрация
   персонализации на защите.
